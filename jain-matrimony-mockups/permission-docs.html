Permissions, Features & Policies

Written for admins, not engineers. Understand what access already exists, what each switch does in daily work, and which permissions need to stay together so screens behave correctly.

Feature

A feature is the admin-friendly package you assign first. Example: Audit Logs, Task Management, or Bio Data Upload And Assign.

Permission

A permission is the exact access switch underneath the feature. It follows this pattern:

module / action / field
Dependency

Some permissions only work when another base permission is also present. This page shows those links clearly.

Policy

A policy does not replace a permission. It narrows the data, such as cities, states, statuses, tiers, payment state, or hidden fields.

Recommended Admin Workflow

This is the simplest and safest order for granting access without creating half-working screens.

1
Start with the business capability

Ask what the user should actually do in daily work, such as search profiles, review duplicates, or manage biodata.

2
Use features before raw permissions

Features are the safer admin layer. They collect the right permissions together so you do not have to memorize technical keys.

3
Check linked permissions

If a permission depends on another one, give both so the screen works correctly instead of opening halfway.

4
Use policies to narrow the data

After deciding what a user can do, policies decide how much of the data they can reach.
